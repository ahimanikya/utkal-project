# Public contributions through GitHub Issues

Ahimanikya Satapathy selected **“GitHub Issues, with submissions visible publicly”**. This is the first delivery channel for corrections, additional knowledge, personal recollections and photograph proposals. The repository is public and Issues are enabled. This workflow and the local issue templates still await release; no test contribution was posted.

## What the visitor experiences

The website prepares a draft locally. Preview, copy and text-download controls work before any handoff. The page identifies GitHub as public: username, issue text and attachments may be visible to anyone. Preparing the link does not submit anything. Opening it sends the encoded draft to GitHub, where the visitor signs in if necessary, reviews the text and chooses whether to submit. For a draft too long for the link, the website offers the complete copied text and a blank issue page.

A posted issue is immediately public. It is not an accepted encyclopedia article. Editing the local draft invalidates the previously prepared link. No account database, email service, server endpoint or automatic posting is introduced.

## Editorial handling

1. **Intake:** the issue URL is the public source record. Acknowledge only when someone actually reviews it; no automatic response deadline is promised.
2. **Triage:** identify the affected entry and distinguish a correction, a research lead, a recollection or a media proposal. Identify duplicates and ask for missing public evidence where needed.
3. **Verify:** check sources and disagreements; preserve the difference between evidence, local belief and personal memory. For photographs, verify creator, source, licence, editing and privacy before incorporating an asset.
4. **Prepare:** turn supported material into a proposed KB/site change linked to the issue. Preserve requested public credit without assuming it proves ownership. AI assists the review and drafting; it does not approve publication.
5. **Human decision:** Founder & Editor-in-Chief Ahimanikya Satapathy makes the final acceptance and publication decision. Contributor status or repository access is a separate human decision.
6. **Publish and resolve:** after an approved release, record the actual article/change link and explain the disposition before closing the issue. Rejection, deferral and duplicate handling should be stated clearly and respectfully.

Do not solicit private contact details, consent documents or identification through public issues. Posting material is not blanket reuse permission. Where rights cannot be established from public evidence, defer reuse until a suitable permission process exists; never put private evidence in this public KB.

## Implementation and activation

The local repository contains `.github/ISSUE_TEMPLATE/knowledge.yml`, `photo.yml` and `config.yml`. The generic prefilled-issue link can work without deployed templates. Templates become selectable only after reaching GitHub's default branch. Website delivery becomes available to public visitors only after the approved website release.

There are no received contributions recorded by this task. The optional contribution-register extension is not activated merely by preparing a channel. On activation, link actual intake to work, decisions and releases using the existing registers; do not create fictional contributors or approval records.
